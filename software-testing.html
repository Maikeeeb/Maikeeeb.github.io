The starting point

Why build it?

A failing input can be large and difficult to understand. Testing should reveal a failure and help isolate the part that triggers it.

My contribution

What I built.

I implemented random-input testing around a supplied QuickSort exercise and a recursive reducer that compares a buggy string transformation with corrected reference behavior.

For a closer technical review

Decisions & tradeoffs.

Open each note for the implementation boundary, tradeoff, and next engineering question.

01An oracle also needs testing

The sort harness checks adjacent ordering, but its loop omits the last adjacent pair. Order alone also misses lost or duplicated values. A stronger oracle compares the entire result with sorted(original), preserving order and membership.

02Reduction needs a precise promise

The reducer removes a character when the mismatch remains. It prints the reduced case but does not propagate recursive return values through every branch. It illustrates failure reduction, not a globally minimal input or a general-purpose ddmin implementation.

Scope & next steps

What this demonstrates.

Coursework with deliberately faulty target code. Deterministic tests should cover empty inputs, last-position defects, preservation of failure, and reducer return values.
